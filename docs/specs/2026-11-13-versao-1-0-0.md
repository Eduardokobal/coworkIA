# Spec da versão 1.0.0 do coworkIA

Aprovada pelo Eduardo junto com o plano da versão 1.0.0.

**Versões:** a versão 1 (sha256 5948cab965998aecac5db47d8cd7723f14479beec983c7b86c335288cabb1344) recebeu CORRIGIR, pelo achado 160, e ANOTAR, pelo 161. A seção "O que mudou da versão 1 para a 2", no fim, liga cada mudança ao seu achado.

**Por quê.** A main ficou completa em 2026-11-12: o último código entrou no PR 19, e o PR 20 (`758dc9e`) fechou a documentação. Em 2026-11-13, o Eduardo perguntou o que faltava para o projeto ficar pronto. O DEV explicou o que foi testado com dados reais e o que não foi: uma conta real do Google, um extrato real do banco e uma exportação de um iPhone. O README já diz isso a quem lê. O Eduardo escolheu pela caixa:
- "Dar como pronto e marcar a v1.0 (Recomendado)";
- "Subir para 1.0.0 no código (Recomendado)", para que o código e a etiqueta digam a mesma versão.

## 1. A versão no código

- **V1. O número.** O 0.1.0 passa a 1.0.0 em três arquivos:
  - `package.json`, no `version`;
  - `package-lock.json`, no `version` da raiz e no do pacote `""`;
  - `src/servidor.ts`, no `version` do `McpServer`, que o cliente MCP recebe ao conectar.
- **V2. O teste.** Um arquivo de teste novo confere que a versão que o servidor informa ao cliente e as duas versões do `package-lock.json` são a do `package.json`. Ele protege contra os números se separarem de novo.
- **V3. O resto não muda:** as ferramentas, as regras, a demonstração e o README.

## 2. A etiqueta e a página de lançamento

- **V4. Quando e onde.** Depois do merge do PR da versão, num roteiro próprio, com o "pode" do auditor e o OK do Eduardo pela caixa. O alvo é o commit do merge, preso pelo hash completo.
- **V5. Como.** Um só comando, `gh release create v1.0.0 --target <hash do merge> --title "coworkIA 1.0.0" --notes-file <arquivo>`. O arquivo é o texto da seção 3, conferido pelo sha256 antes. Pela ajuda do `gh` 2.98.0, quando a etiqueta não existe, o comando a cria, e o `--target` diz o commit. Pela documentação da API ("Create a release"), o `target_commitish` determina de onde a etiqueta é criada. A etiqueta nasce no GitHub, sem passar pelo `git push` nem pelas travas locais, do mesmo jeito que as gravações da CI10 e da CI11 pela API. Se ela é leve ou anotada, e com que autor, as fontes não dizem, e a V6 lê depois.
  - A página não leva anexos enviados pelo DEV. Pela página "About releases", o GitHub inclui sozinho os links do código em zip e em tarball.
  - Ela não abre discussão e não é pré-lançamento.
- **V6. O depois.** O DEV lê pela API a release e compara o texto publicado com o arquivo, sem as quebras de linha do fim. Depois, lê a ref da etiqueta (`gh api repos/Eduardokobal/coworkIA/git/ref/tags/v1.0.0`) e confere o `object.type`:
  - se for `commit`, o `object.sha` tem de ser o hash do merge;
  - se for `tag`, o DEV lê o objeto da etiqueta (`git/tags/<sha>`), e o alvo dele tem de ser o hash do merge.

  Cada conferência é um comando que sai com 1 quando o esperado não bate.
- **V7. Quem é avisado.** A página é pública. Pela documentação da API, criar uma release "triggers notifications". Ela não diz para quem. Em 2026-11-13, pela API, o repositório tinha 0 inscritos, 0 estrelas e 0 forks.
- **V8. A volta.** As releases imutáveis estão desligadas no repositório (`enabled: false`, lido pela API em 2026-11-13). Assim:
  - um erro no texto se corrige com o `gh release edit`;
  - a página e a etiqueta se apagam juntas com o `gh release delete v1.0.0 --cleanup-tag --yes`. O `--yes` pula a confirmação, que num roteiro ninguém responde.

  O que fica mesmo depois de apagar: um aviso já mandado e a etiqueta nos clones que já a buscaram.

## 3. O texto da página de lançamento

O título é "coworkIA 1.0.0". O texto, inteiro, é o do bloco abaixo, sem as linhas da cerca. Ele vira o arquivo do `--notes-file`:

````markdown
O coworkIA é um servidor MCP que roda no seu PC e dá à sua IA ferramentas para ler e fazer a triagem dos e-mails e das conversas exportadas do WhatsApp, ler e resumir os extratos do banco em OFX, consultar a agenda, criticar um rascunho e montar o resumo do dia. Ele nunca envia nada e marca o texto de terceiros como dado.

## O que vem na 1.0.0

- O modo de demonstração, com e-mails, eventos, conversas e extratos inventados, para testar sem conectar nada.
- O modo google, com o seu Gmail e a sua Agenda do Google, só para leitura.
- O modo arquivos, só com as conversas exportadas do WhatsApp e os extratos OFX, sem o Google.
- 13 ferramentas e o prompt `criticar_rascunho`. Uma delas, a `classificar_emails`, recebe os e-mails que a sua IA já leu por um conector próprio e devolve a triagem, sem o login do Google no coworkIA.

## Como foi testado

- 528 testes automáticos, que rodam no GitHub em cada PR para a main e em cada push na main.
- O WhatsApp foi medido com exportações reais do WhatsApp do computador e de um celular Android.

## O que ainda não foi testado com dados reais

- O modo google, com uma conta real do Google.
- Um extrato real de banco: as finanças foram medidas com extratos de exemplo publicados por projetos abertos.
- Uma exportação do WhatsApp feita num iPhone e a citação com o `@` do seu nome.

As limitações conhecidas da triagem, como o "Preciso disso até amanhã." sem data, estão no README.

## Como usar

A instalação, a ligação numa IA, as variáveis de ambiente e os avisos sobre os dados de terceiros estão no [README](https://github.com/Eduardokobal/coworkIA#readme). A licença é a MIT.
````

## 4. Os testes

- **V9.** O teste da V2, com dois casos: o do servidor e o do `package-lock.json`. A suíte passa de 526 para 528 testes, e o CI do PR da versão precisa sair verde antes do merge.

## O que mudou da versão 1 para a 2

- **160, a etiqueta "leve".** A V5 diz só o que as fontes dizem: o comando cria a etiqueta no commit do `--target`, sem passar pelo `git push` nem pelas travas. A V6 lê a ref da etiqueta e confere o alvo, seja ela leve ou anotada.
- **161, a confirmação da volta.** A V8 usa o `--yes`.
- **As observações do auditor.** O "Por quê" diz que o último código entrou no PR 19, e que o PR 20 fechou a documentação. A V7 diz só o que a documentação da API diz sobre as notificações. A V5 diz que o "sem anexos" vale para os anexos enviados, porque o GitHub inclui sozinho os links do código em zip e em tarball.
