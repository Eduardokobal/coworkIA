## 1. O workflow

- **CI1. O arquivo.** `.github/workflows/ci.yml`, com o nome `CI`.
- **CI2. Quando roda.** No evento `pull_request` para a branch `main` e no evento `push` na branch `main`. Nenhum outro evento. O `pull_request_target` nunca é usado, porque ele roda com o token e os segredos do repositório sobre o código de quem abriu o PR.
- **CI3. Os PRs de fork.** O repositório é público, e qualquer pessoa pode abrir um PR a partir de um fork. No evento `pull_request`, o GitHub roda o workflow de um fork com o token só de leitura e sem segredos, e o workflow não tem segredo nenhum. A configuração do repositório já pede a aprovação do Eduardo antes de rodar o workflow de quem contribui pela primeira vez (`approval_policy: first_time_contributors`), e isso não muda.
- **CI4. As permissões.** No topo do arquivo, `permissions: contents: read`, e nada mais. O padrão do repositório já é só leitura (`default_workflow_permissions: read`), e o arquivo deixa isso explícito.
- **CI5. Uma execução por vez, só nos PRs.** `concurrency` com o grupo `ci-${{ github.event_name == 'pull_request' && github.ref || github.sha }}` e `cancel-in-progress: true`. Num PR, o grupo é o do PR, e um push novo cancela a execução anterior. Na main, cada push tem um grupo só dele, pelo hash do commit, então nenhuma execução é cancelada nem fica esperando, e cada merge commit fica com o resultado completo. O grupo único na main é necessário porque o GitHub guarda, em cada grupo, no máximo uma execução rodando e uma esperando: com o `cancel-in-progress: false` e um grupo comum, a que estivesse esperando seria cancelada quando chegasse uma terceira.
- **CI6. O job.** Um só, com o id `verificar` e o nome `verificar`, em `ubuntu-latest`, com `timeout-minutes: 15`. O nome é o da checagem que o ruleset vai exigir (CI10).
- **CI7. Os passos, na ordem.**
  1. O checkout, com `persist-credentials: false`, para o token não ficar gravado no `.git` do runner.
  2. O Node 24, pelo `setup-node`, com `node-version: 24`, sem cache.
  3. `npm ci --ignore-scripts`, que instala as dependências pelo `package-lock.json` sem rodar os scripts de instalação delas, para que um pacote comprometido não rode código na instalação.
  4. `npm run lint`.
  5. `npm run tipos`.
  6. `npm run build`.
  7. `npm test`.
  8. `sh testes-travas/rodar.sh`.

  Um passo que falha para o job, e o job sai vermelho.
- **CI8. As actions, presas pelo hash.** Só duas, ambas do próprio GitHub, cada uma presa pelo hash do commit da versão, com a versão num comentário na mesma linha:
  - `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1`, a v7.0.1, publicada em 2026-07-20;
  - `actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1`, a v7.1.0, publicada em 2026-10-08.

  Os hashes foram lidos pela API do GitHub: as duas tags são leves e apontam direto para esses commits. Nenhuma outra action, nenhum segredo e nenhuma variável de ambiente com valor.

## 3. As configurações do GitHub, depois do merge

As duas mudanças abaixo são gravações no GitHub. Cada uma tem a base, o "pode" do auditor por um roteiro lido, o OK do Eduardo pela caixa e o depois. Elas vêm depois do merge do PR do CI, quando o workflow já rodou verde no PR e na main.

- **CI10. A regra da main.** O ruleset 26699108 ganha a regra `required_status_checks`, com a checagem `verificar`, ligada ao app do GitHub Actions pelo `integration_id`, para que só o GitHub Actions possa marcá-la como verde. O `strict_required_status_checks_policy` fica `false`, então a branch não precisa estar atualizada com a main antes do merge. As três regras de hoje (o PR com merge commit, a proibição do force push e a de apagar a branch) e o `bypass_actors` vazio não mudam.
  - A base: o ruleset como está, lido pela API e guardado na máquina do DEV, e o `app.id` da checagem `verificar` da execução na main, que dá o `integration_id`.
  - A ação: um `PUT` do ruleset inteiro, com as quatro regras.
  - O depois: o ruleset lido de novo, com as quatro regras, `enforcement: active` e o `bypass_actors` vazio.
- **CI11. As configurações de Actions.** O repositório passa a aceitar só as actions do próprio GitHub e exige que elas venham presas pelo hash:
  - `allowed_actions: selected`, com `github_owned_allowed: true`, `verified_allowed: false` e nenhum padrão a mais;
  - `sha_pinning_required: true`.

  O `enabled`, o `default_workflow_permissions: read`, o `can_approve_pull_request_reviews: false` e a `approval_policy: first_time_contributors` não mudam.
  - A base: as quatro leituras de hoje pela API.
  - A ação: os `PUT` das permissões e das actions selecionadas.
  - O depois: as leituras de novo e uma nova execução do CI na main (`gh run rerun`), que mostra que o workflow continua aceito.

  **Correção de 2026-11-12 (achado 158).** A frase "passa a aceitar só as actions do próprio GitHub" promete mais do que a configuração faz. Pela documentação do GitHub, a opção `selected` também aceita as actions e os workflows reutilizáveis do próprio repositório e da conta Eduardokobal. De fora deles, só passam as actions criadas pelo GitHub (as das organizações `actions` e `github`), e toda action precisa vir presa pelo hash completo do commit da versão. O workflow da CI7 usa só duas actions, as duas do GitHub.

## 4. As travas e o CI

- **CI12.** As travas continuam locais. Os hooks (`pre-commit`, `commit-msg`, `pre-merge-commit` e `pre-push`) rodam na máquina de quem commita, e o CI não os roda nos commits do PR. O que o CI roda são os 62 casos de teste das travas (o passo 8 da CI7), que mostram que os hooks funcionam, agora também com o `sh` do Linux (o dash).
- O ruleset, com a CI10, passa a exigir o PR, o merge commit e o `verificar` verde. Um commit que passou pelas travas locais e quebrou um teste não entra na main.

## 5. Antes do PR: as travas num Linux de verdade

- **CI13.** Como o `sh` do `ubuntu-latest` é o dash, e as travas foram feitas e testadas no Git Bash, o DEV rodou antes, num contêiner do Docker da máquina dele, com a imagem `node:24` (Debian, em que o `sh` também é o dash), os passos 3 a 8 da CI7, num clone feito dentro do contêiner, com o fim de linha do Linux. Rodou duas vezes: com o `npm ci` normal e com o `npm ci --ignore-scripts`. O resultado está na seção 7. Os contêineres e a imagem foram apagados no fim.

## 6. Os testes deste ciclo

- **CI14.** O workflow não tem teste automático no repositório. Ele é conferido de três jeitos:
  - o arquivo é lido e comparado com esta spec, linha a linha, pelo DEV e pelo auditor;
  - a CI13, no Docker, roda os mesmos comandos dos passos 3 a 8;
  - a primeira execução no próprio PR é a prova final. Ela precisa sair verde antes do merge.

  O fechamento do plano roda, como sempre, a suíte inteira, o lint, os tipos, o build e as travas na máquina do DEV.

## 8. Fora desta spec

- O runner do Windows, o cache do npm e mais de uma versão do Node.
- A atualização automática das actions (o Dependabot para as actions). As versões ficam presas até um ciclo próprio.
- Conferir no CI os commits do PR pelas regras das travas (o autor, o formato da mensagem e os segredos).
- A análise de código do GitHub (CodeQL).

## O que mudou da versão 1 para a 2

- **138, ANOTAR, a concorrência na main** (o Eduardo escolheu "Cancelar só nos PRs (Recomendado)"). Com o `cancel-in-progress: true` da versão 1, um merge feito enquanto o CI do merge anterior ainda rodava cancelaria essa execução, e aquele merge commit ficaria com a checagem cancelada. A CI5 passou a cancelar só nos PRs. O auditor sugeriu o `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`, mas, com um grupo comum, o GitHub ainda cancela a execução que está esperando quando chega uma terceira. Por isso, a CI5 dá a cada push na main um grupo só dele, pelo hash do commit, e mantém o `cancel-in-progress: true`, que então só age nos PRs.
